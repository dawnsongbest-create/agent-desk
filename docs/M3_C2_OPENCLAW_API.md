# OpenClaw → Agent Desk Local Bridge API v1

M3-C2 exposes three OpenClaw ingress operations on the existing localhost-only Agent Bridge. The adapter can create Delivery, Proposal, and ReadingPlan domain objects only. It cannot directly create or edit Todo, Record, Quote, or Sticky content.

## Connection

- Base URL: `http://127.0.0.1:47321/api/v1`
- Authentication: `Authorization: Bearer <token generated by Agent Desk>`
- Content type for POST requests: `application/json`
- The token is local secret material. Do not place it in source control, command history, screenshots, or logs.
- Agent identity is derived from the authenticated `AgentConnection`. A client-supplied `agent_id` is rejected and is never trusted.

## Capability discovery

```http
GET /api/v1/capabilities
Authorization: Bearer <token>
```

The response reports the Delivery, Proposal, and Reading capabilities supported by API v1.

## Create a Delivery

```http
POST /api/v1/delivery
Authorization: Bearer <token>
Content-Type: application/json

{
  "title": "AI Daily Research",
  "content": "今日 AI 动态：…",
  "type": "research",
  "subtitle": "OpenClaw 每日研究",
  "idempotency_key": "openclaw:ai-daily:2026-08-22"
}
```

`type` accepts `research`, `brief`, or `report`. `idempotency_key` is optional so the minimal Product contract remains valid, but integrations should send a stable value for retry safety. A repeated key with identical content is idempotent; changed content for the same key returns `409 idempotency_conflict`.

The Delivery response contains `data.item.delivery.id` and `data.item.document.id`. Use the Delivery ID as `source_delivery_id` when creating a Reading proposal.

## Create a Proposal

```http
POST /api/v1/proposal
Authorization: Bearer <token>
Content-Type: application/json

{
  "type": "READING",
  "title": "深入阅读 Transformer Architecture",
  "description": "建议阅读核心架构并形成学习记录。",
  "payload": {
    "content": "Transformer Architecture 核心概念",
    "estimated_minutes": 15
  },
  "source_delivery_id": "<delivery-id-from-the-delivery-response>"
}
```

`type` accepts `READING`, `RECORD`, or `TODO` (lowercase aliases are also accepted). A Reading proposal must identify its source Delivery. Proposal creation never mutates the user workspace: only the existing Agent Desk Accept action may create the corresponding Reading Session, Record, or Todo.

For Record and Todo proposals, `payload.content` is the proposed workspace content. For Reading, `payload.content` is the proposed session selection and `estimated_minutes` must be between 1 and 240.

## Create a Reading Plan

```http
POST /api/v1/reading-plan
Authorization: Bearer <token>
Content-Type: application/json

{
  "title": "Transformer Study",
  "daily_minutes": 10,
  "content": "# Transformer Study\n\n每天学习一个核心模块。",
  "schedule_time": "08:00",
  "difficulty": "technical"
}
```

Only `title` and `daily_minutes` are required. `schedule_time` defaults to `08:00`, `difficulty` defaults to `normal`, and omitted content receives a minimal local plan introduction. Reading plan creation remains inside the Reading application service and domain validation.

## Errors and security boundary

| Result | HTTP status |
| --- | --- |
| Missing or invalid token | `401 Unauthorized` |
| Attempted direct Todo / Record / Sticky mutation | `403 Forbidden` |
| Invalid JSON, unknown field, spoofed `agent_id`, or invalid domain payload | `400 Bad Request` |
| Changed payload for an existing Delivery idempotency key | `409 Conflict` |
| Local application service unavailable | `503 Service Unavailable` |

The Bridge listens only on `127.0.0.1`, never logs the token or user content, and routes accepted requests through application services before domain and persistence layers.
